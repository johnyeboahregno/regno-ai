The request lifecycle

1

Route

A multi-signal router classifies task type and output intent, then picks agent, depth, model tier, framework and output budget — and records the outcome to learn from it.

Code: cortex-flow/routing/ — IntelligentRouter, IntentDetector, PlanTimeRouter, ModelTierEvaluator, LearnedScoreProvider, RoutingOutcomeTracker
2

Plan

A plan engine builds phases declaratively. Phases carry their own depth filter — a phase can be included only at quick / standard / deep — so depth changes behaviour without imperative branching.

Code: cortex-flow/v2/ — PlanEngine, DepthStrategy, ModelResolver, PromptEnhancer
3

Orchestrate & fan out

An orchestrator runs phases through queue-backed workers (concurrency-limited), with a per-phase runner and a retry strategist that classifies errors as transient / permanent / recoverable.

Code: v2/Orchestrator.ts, v2/OrchestratorWorker.ts, v2/PhaseRunner.ts, agents/RetryStrategist.ts
4

Grade

A three-layer evaluator scores the output: objective execution metrics, structural output heuristics, then a model-graded quality pass that also extracts insights.

Code: agents/QualityAuditor.ts — audit() + evaluateExecution()
5

Learn

Insights — anti-patterns, proven patterns, cross-cutting wisdom — are written to shared agent memory and injected into every future run via hybrid retrieval (text + recency + semantic vector search).

Code: services/AgentMemoryService.ts, services/WisdomSynthesizer.ts; store cortex_agent_memories + Qdrant cortex_wisdom

Inside the wisdom loop

This is the part worth understanding before you build, because it is what makes the platform behave differently next month than it does today.

  • Shared vs. agent memory — memories keyed with no agent and no user are global: injected into every execution. Agent-scoped memories layer on top.
  • Three categories — error (anti-patterns), pattern (proven approaches), wisdom (cross-cutting principles), each with a default relevance weight.
  • Hybrid retrieval — agent-text + agent-recent + shared-text + shared-recent + semantic vector search, merged per run.
  • Self-maintaining — confirmation counts reinforce repeated lessons; usefulness ratings and a three-strike rule archive bad ones; a scheduled prune removes stale low-value memories; a synthesis pass distils facts into operating principles.

The refine loop you can opt into

generate → grade → regenerate, bounded by cost

The in-execution evaluator-optimizer loop (tracked as AGENT-EVAL-LOOP) wraps the final render: it grades the output, and if it is below target, re-runs the phase with the critique injected as refinement feedback — looping until it hits the target score or the cost ceiling, whichever comes first. Its sibling (AGENT-EVAL-WISDOM) writes each critique back to the shared store as an anti-pattern, so the system needs fewer passes over time. It is opt-in and off by default — you enable it per workflow, so it never multiplies your cost unexpectedly.

Design commitments you can rely on

  • The model never holds the wheel — control flow is deterministic code and a state machine; the model is invoked only inside reasoning nodes.
  • No inline inference on the web tier — all model work is queued to the execution server, so request latency and failure blast radius stay contained.
  • Declarative over imperative — depth, phases, model tiers and presets are configuration, not branching logic, so behaviour changes without code surgery.
  • No silent fallbacks — when something is wrong it surfaces; we fix the root cause server-side rather than paper over it on the client.
