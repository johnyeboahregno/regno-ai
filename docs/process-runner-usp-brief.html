Technical Brief · CMS Platform

The Process Runner

One engine walks any CMS change through every gate of its journey, in two modes behind a single code path: a simulator that never touches the live document, and a persister that performs the real mutations. Your regression smoke-test and your production gate-advance are the same walk — so there is no second implementation to drift, and no mocked test that passes while the real journey is broken. That equivalence is the whole point.

Audience: engineer / technical reviewer Scope: src/apps/cms/server/services/processRunner

The problem it exists to solve

The CMS runs seven distinct process types — cr, pr, sc, msac, msacc, msap, pmc — each a multi-gate journey: raise → submit → QC → QA → IC, then per-sub-process PA / IA / CAN / SW / CA review chains, then completion. Every gate mutates state: it appends history, applies a status delta, extends an audit chain, can spawn sub-process documents, and can branch on rejection, challenge, clarification, hold, withdrawal, or SECAS.

The combinatorial surface — 7 types × ~29 named path variants × 28 gate kinds — is intractable to exercise by hand. The usual coping mechanism is a separate test harness that mocks the mutation while the production route performs it — two implementations that drift until the harness is lying to you. The Process Runner is built so that second implementation never exists.

What makes it different

One walk, two modes

Same orchestration, same step plan, same validator layer. simulate projects synthetic deltas onto an in-memory snapshot; persist routes through the real EXEC executors. No parallel test rig.

The runner is dumb

All branching lives in declarative path strategies that emit a StepSpec[]. The runner just walks the array. New scenario = new strategy, zero runner changes.

Self-checking every step

After each gate: 10 validators (status-delta-applied, audit-chain-row, sub-process-spawn, no-stuck-task…) plus 9 KPI ticks. A run is its own assertion suite.

Process-type agnostic

Differences between CR / PR / SC / MSAC… are read from processDef.nodes, not hardcoded. The generic walk covers all seven; per-type impls supply the mutations.

Time-travel replay

Pass asOf and the runner trims history to that instant and re-derives status — walk a document as it existed at any past point.

Definitions audited too

Static defAudit checks validate the process definitions themselves — gate completeness, action round-trip, cycle triggers — before any walk runs.

The one-engine-two-modes claim, concretely

This is the load-bearing differentiator, so here is the actual dispatch. Each gate executor resolves a per-type implementation and branches on runMode — the same step, the same validators, only the mutation half differs: 

// gateExecutors.ts — single dispatcher, both modes
const impl = findImpl(ctx.processType, gate);
if (ctx.runMode === 'persist') {
  if (!impl.persist)
    return { ok: false, error: `Gate '${gate}' not yet wired for persist on '${ctx.processType}'` };
  return impl.persist(ctx, step);   // real history-append + snapshot rebuild + sub-process spawn
}
return impl.simulate(ctx, step);     // synthetic delta projected onto an in-memory snapshot copy

In persist mode the executors call realGateAction, which deliberately mirrors the mutation half of the live HTTP route /api/cms/records/action — resolving gates[gateId].actions[actionId] from the process def, stamping history, re-snapshotting, and (at IC) spawning the sub-process doc. It intentionally skips notification dispatch and task-cache invalidation so a smoke run stays silent and side-effect-light. The result shape is identical to the synthetic stub, so the validator layer treats both paths uniformly. That uniformity is the USP: the thing you test is the thing that ships.

Architecture at a glance

RunArgs { docId, processType, pathName, runMode, asOf? }
   │
   ▼
pathStrategy(name) ──▶ StepSpec[]        // declarative; owns all branching
   │
   ▼
runner.walk ──┐
   │          ├▶ findExecutor(gate) ──▶ simulate | persist   // 28 gate kinds
   │          ├▶ ALL_VALIDATORS  (×10)  // post-step state checks
   │          └▶ ALL_KPIS        (×9)   // per-step KPI ticks
   │
   ▼
Mongo: cms_process_runs   // one doc per run, embedded step records
   indexes: runId · (docId,startedAt) · (status,startedAt) · resume-key

Everything pluggable comes through a typed interface and a registry: gateExecutors, validators, kpis, pathStrategies, and the defAudit checks. Extending the system is additive — register a function, the runner picks it up.

What's real, and what's still being wired

A brief for a reviewer that overclaims gets discounted, so this is the honest line. The orchestration, validation and scoring framework is complete and correct end-to-end — the walk, the step plan, the validator/KPI layer, persistence, indexing, resume, and time-travel all work. Maturity varies by the mutation layer:

DONESimulate mode — fully usable across all seven types as a deterministic smoke test. The live document is never mutated; safe to re-run.
DONEValidator + KPI layer — 10 post-step validators (including the def/snapshot equivalence check def-snapshot-equivalence) and 9 KPIs, backed by 5 static definition-audit checks (gate-completeness, action-roundtrip, cycle-triggers, sub-process-targets, role-coverage).
DONEPersist plumbing — realGateAction / realCompleteStage mirror the live route's mutation: history append, snapshot rebuild, IC sub-process spawn.
WIRINGPer-type persist executors — wired for the core CR journey first; gates without a persist impl fail loudly with a pointed error ("not yet wired for persist on '<type>'") rather than silently no-op. Tracked as the CMS-PROC-RUNNER-EXEC-* series.
PARTIALTime-travel fidelity — status is re-derived exactly from trimmed history; other derived snapshot fields stay live. Good enough for classification and status validation; full historic rebuild is a follow-up.

How to evaluate it yourself

  1. Read the orchestration: processRunner/processRunner.ts (the walk, persistence, indexes, time-travel).
  2. Read the contract: processRunner/types.ts (RunMode, StepSpec, PathName, the pluggable interfaces).
  3. Trace one scenario: pick happy in pathStrategies.ts and follow the emitted StepSpec[] into gateExecutors.ts.
  4. Drive it from the UI: CMS → Process Runner console — run a simulate walk, then inspect the per-step validator/KPI results and the cms_process_runs record.
  5. Check the guardrails: defAudit/checks.ts and tests/evaluators/registry.ts for the static definition integrity checks.
The takeaway for a reviewer. Most process-test harnesses earn their green checks by mocking the very mutations that break in production. The Process Runner inverts that: the safe simulator and the real mutator are one engine behind one runMode flag, validated by one shared assertion layer, across all seven CMS types and every branch of their journeys. You are not reviewing a test tool that approximates the system — you are reviewing the system, with a switch that decides whether the walk leaves a mark.
