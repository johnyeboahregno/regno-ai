1. Executive Summary

Regno.ai is an AI-powered knowledge and execution platform designed for enterprises that need to ingest, understand, score, and act on large volumes of domain-specific information. At its core, the platform combines a multi-phase AI execution engine (Cortex Flow) with a pluggable knowledge pipeline that crawls, filters, indexes, extracts, scores, and enriches content across any domain. The system is built on a three-server architecture that cleanly separates web serving, real-time communication, and AI execution concerns.

What distinguishes Regno.ai from conventional RAG platforms is its self-improving quality loop. Every AI execution is automatically evaluated by a three-layer QualityAuditor. Insights, patterns, and anti-patterns are extracted and stored as shared memories. These memories are injected into future executions, creating a compounding effect where the platform literally gets smarter with each use. This is augmented by the WISDOM protocol, where LLMs self-annotate operational insights during their own execution, and by a scheduled wisdom synthesis pipeline that distils cross-domain principles from accumulated knowledge.

The platform supports nine specialised AI agents, each with declarative phase templates, depth-aware filtering, cost ceiling controls, and access to 40+ tools. Knowledge scoring is handled by a pluggable engine architecture supporting seven distinct engines (from simple keyword matching to Cohere Rerank v3.5 and upcoming BGE/Zerank/Voyage integrations), organised into a three-layer pipeline that can be configured via quality tier presets. The entire system is orchestrated through BullMQ with 17+ queues, a fast-lane architecture for sub-100ms job pickup, and crash-resilient checkpointing.

Key Value Proposition: Regno.ai is not just a tool for AI-powered analysis — it is a platform that learns from every execution, compounds quality over time through its wisdom system, and provides enterprise-grade reliability through its queue-based architecture with crash resilience and automatic recovery. It turns domain knowledge into a durable, ever-improving competitive asset.

2. Architecture Overview

Regno.ai operates as a three-server architecture with strict separation of concerns. The SvelteKit web server handles UI rendering and API routing but never runs LLM calls directly. The Realtime server manages WebSocket/SSE connections for live streaming. The Execution server runs all AI workloads via BullMQ workers. This separation ensures the web server remains responsive even during heavy AI processing.

SvelteKit Web Server (:5173)

The primary interface layer built with SvelteKit 5 and Svelte 5 runes. Handles all HTTP API routes, JWT authentication, file uploads via GridFS, CMS workflow management, and server-side rendering. This server never makes direct LLM API calls — all AI work is dispatched to the execution server via BullMQ queues. This keeps the web server responsive and prevents LLM latency from blocking user requests.

Realtime Server (:3002)

A dedicated Express server that manages persistent connections for real-time communication. Handles WebSocket connections, Server-Sent Events (SSE) for token streaming during AI execution, progress events, and Redis pub/sub message routing. Clients connect here to receive live updates as Cortex Flow executions progress, including token-by-token streaming, tool call notifications, cost tracking, and phase transition events.

Execution Server (:3003)

The AI workhorse. Runs all BullMQ workers that process AI execution jobs. Houses the DirectClaudeExecutor (which manages iterative LLM conversations), PhaseRunner (multi-phase orchestration), tool execution sandboxes, the QualityAuditor (post-execution evaluation), and all knowledge pipeline workers (crawling, indexing, scoring, synthesis). Designed for horizontal scaling — multiple execution servers can consume from the same Redis queues.

Separation Principle: The SvelteKit server enqueues jobs and returns immediately. The execution server picks up jobs via BullMQ (with sub-100ms fast-lane pickup). Results stream back to the client through the realtime server. This three-way split means a 15-minute deep-dive analysis never blocks the web server, and multiple AI tasks can run concurrently without interference.

3. Database Layer

Regno.ai uses four distinct database engines, each chosen for its specific strengths. MongoDB serves as the primary document store. Qdrant handles vector embeddings for semantic search. Neo4j manages the knowledge graph for entity relationships. Redis provides queue infrastructure, pub/sub messaging, and ephemeral caching.

MongoDB (:27001)

Primary document store. Holds all persistent application data including user records, CMS processes, knowledge facts, agent memories, cortex patterns, execution logs, credentials (AES-256-GCM encrypted), and configuration. Auth: regno:regno, database: regno.

Qdrant (:6334)

Vector database for semantic similarity search. Stores embeddings for cortex patterns and wisdom entries. Uses cosine distance metric. Powers pattern matching, near-duplicate detection (similarity > 0.92), and semantic search for agent memory retrieval.

Neo4j (:7687)

Graph database for knowledge relationships. Stores entity nodes, relationship edges, and pattern sequences. Enables graph-based reasoning, entity connectivity scoring, and relationship traversal for GraphRAG hybrid retrieval during query-time operations.

Redis (:6379)

In-memory data store serving three critical roles: BullMQ queue backend (17+ queues), pub/sub message bus for real-time event routing between servers, and ephemeral cache for frequently accessed data like active sessions and rate limiting counters.

4. BullMQ Queue Architecture

All asynchronous work in Regno.ai flows through BullMQ queues backed by Redis. This provides crash resilience (jobs survive server restarts), priority-based scheduling, concurrency control, and automatic retry with exponential backoff. The platform uses 17+ distinct queues, each with a dedicated worker optimised for its specific workload.

Fast Lane Innovation: Critical queues use drainDelay: 0, which means the worker polls Redis continuously with zero delay between checks. Combined with the execution server's dedicated process, this achieves sub-100ms job pickup latency — from the moment a job is enqueued on the web server to the moment the execution server begins processing it. This is critical for interactive AI tasks where users expect immediate response.

4.2 Crash Resilience

Every long-running job implements checkpointing. The Orchestrator saves phase progress, tool call results, and accumulated context to MongoDB at regular intervals. If the execution server crashes mid-job, the BullMQ retry mechanism re-enqueues the job, and the worker resumes from the last checkpoint rather than restarting from scratch. This is critical for deep-dive analyses that can run for 10-15 minutes and cost $2-4 in API calls. 

  Crash Recovery Flow:

  1. Job starts             -->  Checkpoint 0 saved (initial state)
  2. Phase 1 completes      -->  Checkpoint 1 saved (phase 1 results)
  3. Phase 2, iteration 5   -->  Checkpoint 2 saved (partial phase 2)
  4. SERVER CRASHES
  5. BullMQ retries job     -->  Worker loads Checkpoint 2
  6. Phase 2 resumes at #6  -->  No wasted API calls
  7. Job completes normally -->  Final state saved

5.1 Orchestrator v2

The Orchestrator manages multi-phase execution with the following capabilities:

  • Phase sequencing: Phases execute in order, with output from phase N available as context for phase N+1
  • Checkpoint persistence: State saved to MongoDB after each phase completion and periodically during long phases
  • Pause/Resume: Long executions can be paused by the user and resumed later without loss of progress
  • Cost tracking: Running cost computed after each LLM iteration, with SSE events broadcasting progress
  • Extended thinking: Support for Claude's extended thinking mode for complex reasoning tasks
  • Wisdom extraction: After final phase, extractAndSaveAgentMemories() processes WISDOM annotations
  • Quality evaluation: After successful completion, QualityAuditor runs automatically when enableMemory: true

5.2 Cost Ceiling Loop Control

Rather than limiting AI executions by iteration count (which is unpredictable in cost), Cortex Flow uses USD-denominated cost ceilings. The DirectClaudeExecutor computes running cost after each iteration and manages the budget:

Budget Threshold Action Message to LLM
0-70% Normal execution No intervention
70% Informational alert "$X.XX of $Y.YY used, ~N iterations remaining"
95% Final iteration "Produce your report NOW — budget nearly exhausted"
100% Loop break Execution stops, results returned

5.3 Analysis Depths

Quick Depth

Inline execution via InlineExecutor (no queue). Single-phase, Haiku model, sub-10s response. Cost: ~$0.01-0.05. Used for simple lookups, summaries, and conversational queries. Phases with depths: ["standard", "deep"] are excluded at this depth.

Standard Depth

Queued execution. Multi-phase with Sonnet model. 1-5 minute runtime. Cost: $0.10-1.00. Used for analysis tasks, report generation, and knowledge queries that need tool access. Balanced cost/quality trade-off.

Deep Depth

Queued execution with elevated budget. Multi-phase with Sonnet and cost ceiling ($4.00). 10-15 minute runtime. Cost: $2.50-4.00. Used for deep-dive explorations, comprehensive data analysis, and multi-source research. 25-35 queries typical.

7.3 Phase Templates with Depth Filtering

Agent phase templates use the depths property for declarative, agent-aware filtering. When a phase specifies depths: ["standard", "deep"], it is automatically excluded from quick-depth executions. The filtering happens at plan conversion time, not execution time:

  {

    model: "claude-sonnet-4-20250514",

  }

8. Knowledge Pipeline

The knowledge pipeline transforms raw web content and documents into scored, enriched, queryable knowledge. It follows a zero-waste philosophy — data is never discarded, only tagged for relevancy. The pipeline supports both staged ingestion (crawl-first) and bulk indexing (direct to cortex_index for trusted sources).

1
Crawl

Web content is crawled using configurable depth, domain restrictions, and rate limiting. The CrawlWorker extracts clean text, metadata, and structural information. Content is stored with its source URL in knowledge_seed_status for tracking. Duplicate URL detection prevents re-crawling previously processed pages.

2
Filter (Three-Outcome Relevance)

Every crawled page passes through a three-outcome relevance filter. The LLM evaluates each page against the target domain and produces one of three outcomes: Accept (relevant, proceed to indexing), Reclassify (relevant to a different domain, re-tag and keep), or Drop (genuinely irrelevant, marked as filtered but never deleted). This is the zero-waste principle in action — even "dropped" pages remain in the system with their filter status for future review.

3
Index

Accepted content is indexed into cortex_index with full metadata, domain tags, and initial quality markers. Bulk indexing mode skips the crawl/filter stages and writes directly to cortex_index — used for trusted sources like API documentation or known-good datasets. Contextual chunking (Anthropic approach, 67% retrieval improvement) is available as a configurable option.

4
Extract

LLM fact extraction processes each indexed page and produces 5-20 structured knowledge facts as complete sentences. Facts are stored in cortex_knowledge_facts with entity links, source references, and extraction confidence scores. Entity-domain linking connects facts to the knowledge graph in Neo4j.

5
Score

The pluggable scoring engine pipeline (see Section 9) evaluates each document and fact for quality and relevance. Scoring is three-tiered: embedding similarity as Layer 1 bulk filter, optional graph enhancement as Layer 2, and LLM cross-encoder as Layer 3 judge for the top candidates. Results are stored as scoreHistory arrays for trend analysis.

6
Analyse

Domain-level analysis aggregates facts, entities, and scores into a comprehensive domain profile stored in cortex_domain_analysis. This includes entity type breakdowns, LLM-generated domain taxonomies (subject trees), quality distribution curves, growth trends, stale content alerts, and integrity gap detection.

7
Enhance

Self-healing knowledge enhancement. The "enhance" button triggers LLM re-processing of low-scoring or stale content. The LLM can enrich facts, add missing context, update entity links, and improve content quality. This is the platform's self-healing mechanism — knowledge quality improves over time even without new crawls.

Every AI execution feeds into a quality loop that extracts insights, stores them as shared memories, and injects them into future executions. Over time, the platform accumulates operational wisdom that measurably improves the quality of its output.

Quality Compounds Over Time: The wisdom system creates a flywheel effect. Early executions produce baseline quality. Insights from those executions improve the next round. Patterns that work are reinforced (confirmation count increases). Anti-patterns are recorded and avoided. Cross-domain principles emerge through synthesis. After hundreds of executions, the platform has accumulated a rich library of operational wisdom that guides every new task — producing measurably better results than a fresh system.

10.1 WISDOM Protocol (Self-Annotation)

Nine agents include the WISDOM protocol in their phase prompts. During normal execution, the LLM writes [WISDOM]: <insight> annotations inline with its response. These are extracted by the Orchestrator using regex (\[WISDOM\]:?\s*(.{10,300})) and stored as shared memories with category wisdom and relevance score 0.85. This approach requires zero extra API calls — the LLM self-annotates during its normal work.

WISDOM protocol agents: deep-dive, deep-research, market-research, document-analyst, video-podcast, video-intelligence-scout, general-assistant, code-explorer, data-source-query.

10.2 Five Sources of Shared Memory

1. Seed Quality Principles

seed-quality-principles.cjs bootstraps 18 foundational principles for cold start. Idempotent: running again reinforces existing principles (increases confirmation count) rather than creating duplicates.

2. QualityAuditor

Automatic post-execution evaluation. evaluateExecution() runs after every final phase when enableMemory: true and result.success. Writes anti-patterns, patterns, and wisdom to shared memory.

3. Manual Evaluation (/apple)

Step 8j of the /apple evaluation command bridges Steve Jobs-style assessment insights to shared memory. Writes to both cortex_agent_memories and stevejobs collections.

4. Wisdom Synthesiser

Scheduled task that converts knowledge facts and documents into operational principles via LLM. Phase 1: domain-specific wisdom. Phase 2: cross-concern universal patterns that apply across all domains.

5. Showcase Generation

ShowcaseGenerationWorker stores patterns/errors from scene evaluation and wisdom from scene fixes. All showcase AI work reads quality memories for guidance.

10.4 Memory Governance

  • Confirmation count: Tracks how many times a memory has been reinforced. Well-confirmed memories (count ≥ 3) survive pruning.
  • Usefulness rating: User feedback via admin dashboard. Three strikes (rating ≤ -0.45) triggers auto-archive.
  • Auto-prune: Scheduled task removes stale memories (>90 days unaccessed) with low confirmation counts.
  • Near-duplicate merging: Qdrant similarity search (threshold > 0.92) merges semantically identical memories.
  • Conflict detection: Contradictory memories are flagged for human review via the admin dashboard.
  • Domain tagging: Memories have optional domain field for filtered retrieval by domain.

14. Design Principles & Key Decisions

The platform is built on a set of core design principles that guide every architectural decision. These principles are non-negotiable and inform how new features are designed and implemented.

14.1 Core Principles

Trust the LLM

Instruct the LLM verbosely and trust it to follow instructions. Force compliance through clear prompt instructions, NOT mechanical code restrictions. All registered tools are available — the LLM decides when and when not to use them (like Claude Code). No restrictedTools or requiredTools mechanical enforcement.

Declarative, Agent-Aware Configuration

Phase templates use depths property for declarative filtering. Filtering happens at conversion time, not execution time. No hardcoded condensing logic. Depth filtering is declarative and agent-aware. The system is maximally flexible.

The LLM IS the Template Engine

For data analysis and report generation: single phase, LLM writes complete self-contained HTML. DocumentRenderTool detects complete HTML docs and saves them directly — no template injection. One turn: read data, Python stats, write HTML, save. This mirrors Claude.ai's approach and produces equivalent quality.

Never Run LLM on Web Server

The SvelteKit web server NEVER makes direct LLM API calls. All AI work is dispatched to the execution server via BullMQ. This keeps the web server responsive, prevents memory pressure from long-running AI tasks, and enables horizontal scaling of AI workloads independently.

Never Discard Data

Zero-waste philosophy across the platform. The knowledge pipeline never deletes content — it tags for relevancy. Audit/score/clean operations tag only; deletion is master-level only. Even "dropped" content from the relevance filter is preserved with its status for future review.

Slide-to-Confirm for Destructive Actions

Every delete/archive across the platform uses a trash icon that reveals a SlideToConfirm component (slide 85% to trigger). No browser confirm() dialogs. Consistent UX pattern that prevents accidental data loss.

14.2 Key Architectural Decisions

Rejected: LLM calls on web server
  • Blocks event loop during 10-15 minute deep analyses
  • Memory pressure from multiple concurrent LLM sessions
  • Cannot scale AI workload independently
  • Crash in LLM processing takes down web server
Chosen: Dedicated execution server + BullMQ
  • Web server stays responsive under any AI load
  • Crash-resilient with checkpoint recovery
  • Horizontal scaling by adding execution servers
  • Priority queues ensure interactive queries are fast
Rejected: Mechanical tool restrictions
  • restrictedTools arrays blocked valid tool usage
  • requiredTools forced unnecessary tool calls
  • Combinatorial explosion of restriction configurations
  • LLM fought against restrictions, wasting tokens
Chosen: Trust the LLM + prompt guidance
  • All tools available; LLM chooses based on task
  • Phase prompts carry behavioural guidance
  • No mechanical enforcement overhead
  • Higher quality output with fewer wasted iterations
Rejected: Iteration-based loop control
  • Fixed iteration count is unpredictable in cost
  • Simple queries waste iterations; complex ones run out
  • No way to budget across different model costs
  • Checkpoint messages at fixed intervals add noise
Chosen: USD cost ceiling with budget alerts
  • Predictable spending per execution ($4 max for deep-dive)
  • LLM gets budget awareness at 70%, urgency at 95%
  • Works across different model costs automatically
  • maxIterations = 200 as safety net only
Rejected: Separate analysis + report phases
  • Phase 2 (analyse) + Phase 3 (report) = pure duplication
  • Phase 3 just reformatted Phase 2 output into HTML
  • 1350 words of prompts for two phases vs 400 for one
  • Extra LLM call with no quality improvement
Chosen: LLM writes complete HTML in one phase
  • Single phase: data query + Python stats + HTML report
  • 70% prompt token reduction
  • Complete HTML detected by DocumentRenderTool and saved directly
  • Design Pillar 3: The LLM IS the Template Engine

15. Platform USPs

These unique selling points differentiate Regno.ai from conventional RAG platforms and AI tooling. Each USP represents a deliberate architectural choice that compounds into a significant competitive advantage.

Self-Healing Knowledge

The "enhance" button triggers LLM re-processing of low-scoring or stale content. Knowledge quality improves over time even without new crawls. Combined with auto-audit (daily + 6h integrity checks), the knowledge base actively maintains itself.

7 Pluggable Scoring Engines

From free keyword matching to premium neural rerankers (Cohere, BGE, Zerank, Voyage). Mix and match engines across a 3-layer pipeline. Quality tier presets (Good/Better/Best/Ultimate) make it simple to balance cost vs accuracy.

Zero-Waste Ingestion

The three-outcome relevance filter (accept/reclassify/drop) never deletes data. Even dropped content is preserved with metadata for future review. Reclassified content finds its correct domain automatically. Nothing is wasted.

WISDOM Protocol

LLMs self-annotate operational insights during execution with zero extra API calls. Nine agents include the protocol. Extracted insights are stored as shared memories and injected into all future executions. The platform literally teaches itself.

Fast Lane Execution

Sub-100ms job pickup via drainDelay: 0 continuous polling. Quick-depth queries execute inline via InlineExecutor, bypassing the queue entirely. Interactive AI feels instantaneous.

Universal Job Console

Single dashboard to monitor all 17+ queues, view job status, retry failed jobs, inspect execution logs, and manage priorities. Full visibility into every background process across the entire platform.

Contextual Chunking

Anthropic's contextual chunking approach that reduces retrieval failure by 67%. Each chunk includes surrounding context from its parent document, dramatically improving semantic search accuracy. Available as a configurable option per domain.

Multi-Framework LLM Support

Supports multiple LLM providers (Anthropic Claude, OpenAI GPT, Google Gemini) with per-phase model selection. Extended thinking support for Claude. Cost ceiling works across all providers automatically.

GraphRAG Hybrid Retrieval

Combines vector similarity (Qdrant), graph traversal (Neo4j), and keyword matching into a unified retrieval pipeline. Entity connectivity scoring enriches results with relationship context that pure vector search misses.

Crash-Resilient Execution

BullMQ checkpointing saves phase progress and tool call results periodically. Server crashes during 15-minute analyses resume from the last checkpoint — no wasted API calls. Retry strategies with exponential backoff handle transient failures.

Brain Browser

Unified search interface across all 11+ knowledge types (facts, patterns, memories, index entries, domain analyses, and more). A single query searches the entire knowledge substrate with relevance ranking.

Declarative AI Configuration

82 foundation patterns across 8 categories. Pattern evolution with confidence scoring, usage tracking, and automatic decay. Three-store sync (MongoDB + Qdrant + Neo4j). Patterns replace hardcoded logic with flexible, LLM-readable configuration.
